# 飞书员工一键发放 Key

实现：独立的管理员发放模块，复用全站 SMTP、用户和 API Key 服务。所有测试和构建在 GitHub Actions 执行。保存设置或生成预览不会创建 Key、充值或发送邮件。

## 已有能力与缺口

- `frontend/src/views/admin/UsersView.vue` 已有 `FeishuDirectorySync` 入口，新增按钮可紧随其后。
- 系统设置的「邮件设置」已有 SMTP 主机、端口、账号、密码/授权码、发件邮箱、发件人名称、TLS、连接测试和测试邮件。`EmailService.GetSMTPConfig` / `SendEmail` 读取同一套站点配置，可以直接复用发送能力；本次只读查询确认生产 SMTP 主机尚未配置。
- 目前 SMTP 配置和测试邮件界面受 `email_verify_enabled` 控制。现已让发信配置独立展示，避免只用飞书登录的站点为了发信而被迫启用邮箱注册验证。
- `FeishuDirectoryService` 的接口模型声明并解析 `open_id`、员工状态、`enterprise_email` 和 `email`，通过飞书身份创建或同步本站普通用户。模型支持字段不等于历史同步已实际获取并保存邮箱，线上核查结果见下节。
- `syncFeishuContactEmail` 只在用户仍使用占位邮箱时补全联系人邮箱，企业邮箱优先。它不会持续覆盖已填入的邮箱，也不保留两个独立的邮箱字段。因此发送 Key 必须读取新的飞书通讯录快照，不能直接把用户列表中的邮箱当作最新企业邮箱。
- `APIKeyService.Create` 已支持指定所有者、单个或多个分组、额度上限、过期时间、窗口限额及并发限制。管理员 API 尚无员工批量创建并投递 Key 的完整流程。
- 现有 `EmailQueueService` 是验证码和密码重置的内存队列，不适合直接承担需要重启恢复、逐人状态及补发的批量发放。可借鉴 `AutoCreditEmailWorker` 的持久化任务模式。

## 企业邮箱只读核查结果

本次只读查询生产数据库并调用当前飞书应用的读取接口，没有执行同步写入、修改飞书权限或发送邮件。读取应用权限、完整部门/员工快照，并抽查 3 位员工的单用户接口；同时按现有同步的首次出现去重规则复核。

| 检查项 | 结果 |
| --- | --- |
| 飞书通讯录员工 | 20 位，9 个部门（含根部门） |
| 返回有效 `enterprise_email` | 20/20，20 个不同地址 |
| 返回有效 `email` | 20/20，20 个不同地址 |
| 不同部门返回同一员工邮箱不一致 | 0 |
| 当前应用/企业身份对应本站用户 | 20/20 |
| 企业邮箱被其他本站用户主邮箱占用 | 0 |
| 本站飞书用户仍使用占位邮箱 | 20/20 |
| 当前应用通讯录、邮箱及受雇信息读取权限 | 接口返回已获批 |
| 生产 SMTP 主机 | 尚未配置 |

当前字段名、字段类型和读取权限可以排除为本次实时读取的阻碍；飞书确实提供了邮箱。历史同步时是否已经返回这些值、是否在某次保存中跳过，尚不能从现有记录唯一确定原因。当前 Redis 未保留一条可供回溯的同步任务，源码也没有逐人邮箱同步结果记录，不能据此宣称保存链路已修复或 20 人已经回填。

实施时优先补齐邮箱回填与结果诊断：企业邮箱已获取、已回填、未变化、受用户自行绑定保护、邮箱冲突、上游未返回、保存失败分别统计。现有 `updated` 只代表用户经过同步处理，即便邮箱为空而没有写入也会计数，不能充当邮箱成功凭据。

发 Key 前以当前企业身份校验后的真实企业邮箱为收件来源，先完成可核对的邮箱回填/预检；不能把当前列表中的占位邮箱用于投递。

## 页面与设置

工具栏顺序：同步飞书用户 → 一键发送 Key → 设置（齿轮）→ 创建用户。

使用本站按钮、弹窗、下拉框和开关。设置有可见入口，右键可以作为额外快捷入口。配置保存在服务端，对管理员共享，不仅存于当前浏览器。

配置包含：

| 参数 | 行为 |
| --- | --- |
| 发放对象 | 已勾选员工，或当前企业全部符合条件的员工；全部范围不限于当前分页 |
| 绑定分组 | 选择一个或多个启用分组；只追加本次明确授予的权限，不覆盖原分组权限 |
| 余额处理 | 默认沿用现有余额；可选择首次发放赠额并填写每人金额 |
| Key 额度 | 单独配置这把 Key 的总消费上限，明确标注 0 表示不限额 |
| 高级限制 | 有效期、日/周等窗口额度、Key 并发；默认继承现有规则 |
| Key 名称 | 例如「员工姓名 · 企业发放」，不以邮箱或姓名识别账号归属 |
| 收件邮箱 | 默认只使用飞书返回的企业邮箱；如允许回退到联系邮箱，必须作为显式选项 |
| 邮件内容 | 标题、简短说明、API 地址、Key、分组、余额/额度与有效期；复用站内邮件模板能力 |

点击发放按钮先展示本次收件名单、跳过原因、绑定分组、每人赠额及预计总赠额，再执行本次任务。保存设置不会触发发送。

## 发放流程

1. 验证管理员权限和站点现有的敏感操作认证策略，读取 SMTP、飞书和发放配置；首次发送前可沿用现有测试邮件入口验证发信账户。
2. 从当前配置的飞书应用获取完整通讯录快照。以当前 `provider_key`（应用与企业）和 `open_id` 匹配本站身份，再定位用户 ID；不按邮箱、姓名或前端提交的收件地址匹配。
3. 只处理当前企业中已激活、未冻结、未离职的员工及本站启用的普通用户。尚未创建本站用户的员工显示“请先同步飞书”，由已有同步入口创建后再预览。缺失企业邮箱、占位地址、邮箱冲突或身份不匹配显示明确的跳过原因。
4. 检查选中的分组是否启用、用户是否可绑定。标准余额分组可以按本次配置追加授权；订阅分组必须已有有效订阅，否则在执行前列出原因，不用赠额代替订阅。
5. 根据专用发放记录创建或取得归属于该员工的 Key；检查有效期、状态和剩余额度。被撤销、删除、禁用或已失效的已发 Key 不因补发自动恢复，需管理员明确处理。
6. 若开启首次赠额，将赠额、账本、发放记录和待发送任务以事务保护；使用固定业务标识确保同一员工不会因新批次、刷新、超时或改设置重复领取。使用原子余额增量并失效计费缓存，不覆盖并发扣费或现有余额。
7. 后台逐人发送，一人一封；邮件只包含该员工自己的 Key 与使用说明。发送任务保存进度，管理员刷新或服务重启后仍可继续查看结果。

“收到即可用”的前提是绑定分组有效，用户具备对应权限，账户余额/订阅和 Key 额度足够；预览应把不满足条件的用户单独列出。平台或分组本身的上游故障不属于发放成功的保证范围。

## Key、余额与重试

- 用户已确定 Key 归属策略：每位员工维护一把企业发放专用 Key，首次创建，以后补发同一把；员工自行创建的其他 Key 保留。
- 账户余额是调用费用来源；Key 总额度和窗口限额是消费约束。配置 Key 额度不会产生账户余额，也不会替代订阅权益。
- 首次赠额与邮件补发独立记账。重复点击、重试失败邮件、服务重启均不再次建 Key 或再次赠额；更换分组配置也不隐式重置已用额度或重新赠额。
- 初始赠额应使用独立的赠送账本类型并保持审计，遵循站点已有赠送规则；不能直接套用会触发充值返佣的 `BatchRechargeUsers` 来处理无偿赠额。现有 VIP 自动垫付规则继续生效，预览清楚区分现有余额与本次赠额。
- 任务和每位员工的发放记录使用数据库唯一约束及并发锁；仅靠前端禁用按钮、短期 Redis 标记或请求幂等键不足以防止跨批次重复赠额。
- 对确定失败的邮件提供重试，仅重发原 Key。SMTP 提交结果不确定时单独标记，允许管理员核对后补发；不承诺邮件绝对只出现一次。
- 状态区分待发送、发送中、邮箱服务已接受、失败、跳过、提交结果不确定；SMTP 接受不等同于进入收件箱或员工已阅读。
- 发送前再次验证用户、Key、企业配置和收件邮箱归属，避免排队过程中撤销权限或切换飞书应用后仍向旧收件人发送。
- 发放日志记录操作者、员工 ID、Key ID、分组、赠额和发送状态，不保存完整 Key 或完整邮件正文。待发送任务引用 Key ID，在发送阶段按身份校验后读取 Key。

## 实现与验证边界

新增独立前后端模块、专用配置、发放记录和发送队列；共享用户页面、路由、服务组装和邮件设置只接入必要入口。专用文件纳入 `custom/protected-paths.txt`，共享文件继续正常合并上游。

测试和构建使用 GitHub Actions，不在本机安装依赖或执行测试。关键回归包含当前企业身份限制、真实企业邮箱选择、跨页范围、分组/订阅权限、账户余额与 Key 限额区别、并发重复点击、赠额账本事务、失败补发、重启恢复、已撤销 Key 和 SMTP 不确定状态。

## 官方接口核对

- 通讯录部门员工列表：<https://open.feishu.cn/document/server-docs/contact-v3/user/find_by_department>
- 飞书官方说明邮箱等字段需要独立的读取权限，且只能获取应用通讯录权限范围内的数据：<https://open.feishu.cn/document/faq/server-side-generic-questions/app-permission>

现有代码已声明 `contact:user.email:readonly` 等通讯录读取权限；声明不代表企业管理员已审批或相关邮箱一定有值。无权限与员工未填写邮箱分别呈现，不拼造邮箱。

## 持久化与运行恢复

配置、批次和每位用户的专用 Key 回执使用现有 `settings` 表的独立命名空间持久保存；共享数据库事务及 PostgreSQL advisory transaction lock 跨实例串行化转换。用户级回执不随批次过期，记录 Key ID 和首次赠额，不复制完整 Key。Key、授权追加、首次赠额、赠送账本及回执在同一事务中提交，无需新增共享模型或执行本地代码生成。

后台每次处理一名员工，任务租约 5 分钟，正常处理上限 2 分钟。服务重启后等待旧租约失效再接管；遗留 `sending` 标记为结果不确定，不自动重发。失败邮件可补发；不确定邮件需要管理员开启明确的补发选项。已发送邮件不进入失败补发。

首次启动自动回填当前应用下现有飞书用户的占位邮箱：通讯录读取完整成功后，按已有 auth identity 定位用户，只更新占位邮箱。不会创建用户、替换应用、发放 Key、赠额或发送邮件。上游读取失败或仍有缺失邮箱时每 5 分钟再试。扫码登录缺少企业邮箱时，以同一 open_id 读取单员工通讯录补取；缺少可选权限不阻断原有登录。

发信前重新核对当前应用指纹、员工状态、身份、实际邮箱、Key 状态及权限。邮件模板固定并进行 HTML 转义。系统设置的邮件配置与邮箱注册验证开关独立。共享路由、页面、SMTP 服务及装配继续正常合并上游，专用模块列入定制保护清单。
